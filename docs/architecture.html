Headboard: web, mobile, API и общее ядро

Персональная канбан-доска «разгрузки головы». Один монорепозиторий, четыре пакета, одна доменная логика. Документ описывает границы слоёв, модель данных, синхронизацию, контракт API, авторизацию, AI-контур, дизайн-систему, тесты и известные ограничения.

1. Обзор

Репозиторий устроен как npm workspaces. Всё, что можно вычислить без пользовательского интерфейса, вынесено в packages/core и покрыто тестами; три приложения только рендерят результат и вызывают действия стора.

2. Слои и потоки данных

Правило зависимостей: apps/* → packages/core → ничего. Ядро не импортирует React, DOM или React Native, поэтому одинаково исполняется в браузере, в Hermes и в vitest под Node. Единственные побочные эффекты ядра сосредоточены в api.ts (fetch) и sync.ts (таймеры), и оба получают зависимости через параметры.

4. Модель данных

Одна и та же форма используется в сторе клиентов, в JSON API и в DTO на сервере. Время везде в миллисекундах эпохи, отсутствие значения передаётся как null, а не пропуском поля.

type Priority = 0 | 1 | 2                 // High · Medium · Low
type Status   = 'inbox' | 'focus' | 'waiting' | 'done' | 'archived'

interface Task {
  id: string; title: string; proj: string | null; pr: Priority; status: Status;
  touched: number; created: number; due: number | null; snoozedUntil: number;
  recur: 'weekly' | null; tags: string[]; note: string; chat: string | null;

interface Comment  { id; text; at: number }
interface Project  { id; name; color: string }     // цвет проекта: данные пользователя, не токен
interface User     { name; email; provider: 'Google' | 'Apple'; initials }
interface CaptureItem { title; pr; tags; proj: string | null }

5. Состояние клиентов

В web и mobile один стор zustand, разделённый на персистентную и UI-часть. Действия стора одинаково названы в обоих приложениях, поэтому поведение совпадает.

Персистентная часть

tasks, projects, projFiles, digestText, digestAt, notifyStale, user, lang, theme, showDone, token. Ключ headboard-v1: web в localStorage, mobile в AsyncStorage. При загрузке без сохранённой темы берётся системная.

UI-часть

Открытая задача (sel / mSel), фильтры (поиск, приоритет, проект), capture, snooze-пикер, предпросмотр файла, меню профиля, drag-состояние, тост. Не сохраняется.

Действия

moveTask, markDone, toggleDone, bump, keep, snooze, archive, restore, deleteTask, setPriority, addComment, attachFiles, removeFile, addTasks, setLang, setTheme, signIn, setAuth, signOut, toast. Каждое обновляет touched там, где прототип это делал. archive ставит archivedAt, restore возвращает в Inbox и сбрасывает его, deleteTask удаляет запись насовсем.

Выборки

Компоненты фильтруют live() (без архива), затем зовут sortAutoBump или sortDone из ядра с текущим now из хука useNow (обновляется раз в минуту).

Различия web и mobile сводятся к именам UI-полей (sel против mSel, capOpen против mCapOpen) и к хранилищу. Выход из аккаунта в API-режиме очищает локальные данные, в локальном режиме оставляет их.

6. Синхронизация

Движок createSyncEngine(adapter) в core/sync.ts реализует offline-first модель: клиент всегда работает с локальным стором, движок подписан на изменения и переводит их в вызовы API. Адаптер даёт ему getState / setState / subscribe / fileToPart / onUnauthorized / onError / baseUrl / timeZone; движок отдаёт start / flush / refreshSettings / refreshTasks / stop. Web-адаптер занимает 27 строк, mobile 33.

Правила движка

  • Снимки. Для каждой задачи и проекта хранится JSON последнего успешно отправленного состояния. Новый id → POST, изменённый JSON → PATCH полным телом, исчезновение из стора → DELETE. Архивирование это PATCH status='archived' с archivedAt; настоящий DELETE уходит только из экрана архива после подтверждения.
  • Очередь. Все запросы идут через одну promise-цепочку, поэтому порядок сохраняется и параллельных гонок нет. start() защищён от повторного входа (React StrictMode вызывает эффекты дважды).
  • Файлы. fileToPart решает, что загружать: в web это data URL, превращённый в Blob; в mobile это file:// или content://, переданный как RN-дескриптор {uri, name, type}. После загрузки движок подменяет FileRef на серверный с абсолютным src.
  • Ошибки. 409 id_exists переводится в PATCH. Любая другая ошибка забывает снимок и ставит повтор через 3 секунды. 401 на старте вызывает onUnauthorized, клиенты делают signOut.
  • Настройки. lang, theme, showDone, digestText плюс зона клиента timeZone сравниваются как одна строка и пишутся PUT /settings с дебаунсом. Дайджестом владеет сервер: null в теле означает «без изменений», а если ответ на PUT несёт более новый digestAt, движок принимает серверный текст.
  • refreshSettings(). Повторное чтение GET /settings с принятием более нового дайджеста; web вызывает при возврате вкладки в фокус и раз в 15 минут, mobile при выходе на передний план.
  • refreshTasks(). Перечитывает GET /tasks?includeArchived=true и сливает серверные изменения: неизвестные локально задачи добавляются, известные заменяются, если серверный touched не старше локального; локальные правки, ещё не отправленные, побеждают и уйдут обычным flush. Так на клиент попадают переносы дат из Google Calendar и события, ставшие задачами.

8. Авторизация

  • Google. GoogleVerifier проверяет id-token через Google.Apis.Auth по списку аудиторий Auth:GoogleClientIds (у web, iOS и Android свои client id). Web присылает не токен, а authorization code из popup Google Identity Services: сервер обменивает его на oauth2.googleapis.com/token с Auth:GoogleWebClientId и Auth:GoogleClientSecret, затем проверяет полученный id-token. Секрет не покидает бэкенд.
  • Apple. AppleVerifier тянет JWKS Apple через OpenIdConnect-метаданные и проверяет подпись и аудиторию из Auth:AppleClientIds (Services ID для web, bundle id для iOS). Имя приходит в теле запроса, потому что Apple отдаёт его один раз.
  • Пользователь. Upsert по (provider, subject); инициалы это первые буквы двух слов имени.
  • Web. lib/providers.ts подгружает скрипты GIS и Apple JS по клику. Google: initCodeClient с ux_mode: popup → code → POST /auth/google. Apple: AppleID.auth.init с usePopup → id_token и имя → POST /auth/apple. Кнопки остаются собственными, без логотипов провайдеров.
  • Mobile. Apple на iOS через expo-apple-authentication (нативный лист, identityToken с аудиторией bundle id). Google через expo-auth-session useIdTokenAuthRequest в системном браузере со схемой headboard://; требует development build, не Expo Go. Apple на Android недоступен, кнопка ведёт на dev-логин.
  • Фолбэк. При отсутствии client id провайдера клиент вызывает POST /auth/dev (только Development); без API используется мок-пользователь прототипа. Отмена popup и сбой показываются тостом.

9. AI-контур

Прототип вызывал window.claude.complete; в продукте этот вызов заменён серверными эндпоинтами, чтобы ключ не покидал бэкенд. Промпты объявлены дважды и обязаны совпадать: в core/capture.ts и core/digest.ts для документации и локального парсинга, в Ai/Prompts.cs для запросов.

Извлечение задач

Текст и список проектов → JSON-массив {title, priority 0|1|2, tags[≤2], project|null}. Сервер вырезает от первой [ до последней ], клампит приоритет, обрезает title до 90 символов, сопоставляет имя проекта с id. Пустой результат на клиенте заменяется heuristicExtract.

Дайджест

Статистика digestStats и язык → 2–3 предложения без markdown. Без ключа сервер отвечает 503, клиент берёт cannedDigest с ротацией по digestSeed. Текст и время обновления хранятся в настройках и синхронизируются; утренний выпуск генерирует планировщик на сервере (см. раздел 6).

Клиент Anthropic

POST https://api.anthropic.com/v1/messages, заголовки x-api-key и anthropic-version: 2023-06-01, max_tokens 800, модель из Anthropic:Model (по умолчанию claude-sonnet-5). В тестах подменяется HttpMessageHandler.

Утренний дайджест по расписанию

DigestScheduler (hosted service в API) просыпается каждые Digest:CheckIntervalSeconds (60 с) и для каждого пользователя проверяет чистое правило DigestSchedule.IsDue: локальное время в его зоне (Settings.TimeZone, IANA-идентификатор, клиенты присылают его в PUT /settings; без него UTC) прошло Digest:Hour (8), и за сегодня дайджеста ещё не было. Тогда DigestService считает статистику по тем же правилам, что core/digestStats (границы дня в зоне пользователя), запрашивает текст у Anthropic общим промптом или берёт канонический вариант (cannedDigest, порт из ядра, вариант по номеру дня) и сохраняет DigestText и DigestAt. Ручное «Обновить» на клиенте тоже ставит DigestAt через PUT /settings, поэтому планировщик не перетирает его в тот же день. Клиенты подхватывают новый текст через refreshSettings() движка синхронизации: web при возврате вкладки в фокус и раз в 15 минут, mobile при выходе приложения на передний план; в карточке дайджеста показывается «обновлено 08:00».

Двусторонняя синхронизация с Google Calendar

Подключение отдельное от входа: POST /calendar/connect отдаёт consent-URL с scope calendar и access_type=offline, state подписан HMAC на Jwt:Secret (uid, returnUrl, срок). Callback GET /calendar/oauth/callback меняет code на refresh-token (тот же web-клиент Google) и сохраняет его в CalendarLinks, затем редиректит на returnUrl?calendar=connected|denied|error (web: адрес приложения, mobile: headboard://calendar через openAuthSessionAsync). Refresh-token живёт только на сервере.

CalendarSyncScheduler (hosted service) делает полный проход по подключённым пользователям раз в Calendar:PollIntervalSeconds (300 с) и немедленные проходы по «толчкам» от мутаций задач и кнопки «Синхронизировать». CalendarSyncService.ReconcileUserAsync: при первом проходе создаёт календарь «Headboard»; удаляет события задач, стёртых с прошлого прохода (PendingDeletesJson); читает входящие изменения инкрементально по syncToken (410 → полная перечитка); выталкивает исходящие. Правила: задача зеркалится, пока у неё есть срок и она не done/archived, как событие на весь день с extendedProperties.private.headboardTaskId; отпечаток CalendarHash (title, дата, note) избавляет от лишних запросов и позволяет отличить эхо собственного push от правки пользователя; входящее применяется по правилу «последний пишущий» (event.updated против task.touched); отменённое событие снимает срок с задачи; событие, созданное в календаре «Headboard» руками, становится задачей в Inbox и помечается обратно. Клиенты подтягивают серверные изменения задач через refreshTasks() движка синхронизации (слияние по touched) при возврате в фокус и после «Синхронизировать».

Push-напоминания о забытых задачах

StaleNotifier (hosted service) раз в день после Notify:Hour (9) по зоне пользователя проверяет тех, у кого включён Settings.NotifyStale, по тому же правилу DigestSchedule.IsDue с маркером LastStaleNotifyAt. Если digestStats находит забытые задачи, StaleMessage собирает текст («Забытых задач: N», «“…” ждёт уже X дн.») с deep link /?view=review, а PushDispatcher рассылает его на все устройства из PushSubscriptions: браузеры через Web Push (библиотека WebPush, VAPID-ключи Push:*), мобильные через Expo Push API по токену expo-notifications. Ответы «устройство исчезло» (404/410, DeviceNotRegistered) и пять подряд ошибок удаляют подписку. Web: public/sw.js показывает уведомление и по тапу фокусирует вкладку с ?view=review; подписка создаётся из тумблера «Напоминания» в меню профиля (lib/push.ts: разрешение → pushManager.subscribe с VAPID-ключом из GET /push/config → POST /push/subscribe). Mobile: тот же тумблер в профиль-шторке, токен через getExpoPushTokenAsync (нужен EAS projectId и development build), тап обрабатывает addNotificationResponseReceivedListener и переключает mView.

apps/mobile
├─ App.tsx                    шрифты, splash, ThemeProvider, Root (Header + ScrollView + TabBar + шторки)

  • Навигации нет: один уровень экранов переключается полем mView в сторе, как в прототипе. Таб-бар с FAB «+» рисуется поверх контента, контент имеет нижний отступ 110. Экран архива открывается из профиль-шторки, в таб-бар не входит.
  • Шторки это Modal с анимацией translateY 40 → 0, ручкой 40×4 и учётом safe-area снизу. Смена статуса реализована выпадающим списком в стиле select, потому что в RN нет нативного select.
  • Архив: строка «Archive · N» в профиль-шторке переключает mView на archive; карточки с датой архивирования, Restore и двухшаговым Delete; шторка тикета показывает бейдж вместо статуса.

  • Android использует тот же код; отличия только в insets и в тени (elevation).
  • Dev-флаги для проверки без тапов: EXPO_PUBLIC_DEV_AUTOLOGIN, DEV_RESET, DEV_VIEW, DEV_THEME, DEV_LANG, DEV_SHEET.

15. Ключевые решения

  • Прототип побеждает README при расхождениях: Golos Text вместо упомянутой Literata, четыре пункта навигации с Digest, чипы приоритетов в шапке Board, без точки у активного пункта меню. Зафиксировано в docs/superpowers/specs/2026-09-08-headboard-implementation-design.md.
  • Логика в ядре, а не в компонентах, чтобы web и mobile считали одно и то же и тесты не требовали рендера.
  • Offline-first с клиентскими id: работа без сети и последующая синхронизация без переписывания ссылок; сервер только проверяет коллизии.
  • Полный PATCH вместо гранулярных эндпоинтов для комментариев и файлов в потоке синхронизации: проще диф, меньше состояний; гранулярные эндпоинты сохранены для будущих клиентов.
  • AI только через сервер, ключ не попадает в клиентские бандлы; локальные эвристики остаются как фолбэк.
  • Демо-данные не в продукте: сид загружается динамическим импортом только в dev-сборках.
  • Push только по делу. Одно уведомление в день и только при наличии забытых задач; текст считается на сервере из тех же правил, что и дайджест. Каналы спрятаны за IPushSender, поэтому web и mobile добавляются и тестируются одинаково, а «мёртвые» подписки удаляются сами.
  • Календарь: отдельный календарь «Headboard» и поллинг. Не трогаем основной календарь пользователя, зеркалим только задачи со сроком; входящие изменения читаем инкрементально каждые 5 минут и сразу после правок вместо push-каналов, которым нужен публичный https.
  • Дайджест генерирует сервер, а не клиент по таймеру. Только API работает постоянно и знает все данные; клиенты лишь присылают зону и подхватывают результат. Статистика посчитана заново на сервере по правилам ядра, промпт общий.
  • Архив как статус, а не корзина. Архивирование остаётся обратимым PATCH, удаление явное и двухшаговое; экран архива в web получил пятый нав-пункт, в mobile живёт в профиль-шторке, чтобы не ломать таб-бар из четырёх вкладок с FAB.
  • Четыре дополнительных токена для цветов прототипа вне таблицы вместо литералов, чтобы правило «только токены» проверялось автоматически.

16. Ограничения и следующие шаги

Это состояние main на 2026-09-09. Пункты ниже требуют решений или внешних учётных данных.
  • auth Реальные потоки Google/Apple реализованы, но включаются только при наличии client id: Google Cloud (web, iOS, Android клиенты), Apple Developer (App ID с Sign in with Apple, Services ID с https return URL; localhost Apple не принимает). Apple на Android не поддержан.
  • db Миграции EF сгенерированы для SQLite; PostgreSQL создаёт схему через EnsureCreated(). Перед эволюцией схемы в проде нужны отдельные Postgres-миграции.
  • push Напоминания включаются VAPID-ключами на сервере (web) и EAS projectId плюс development build (mobile); в Expo Go удалённые push не работают. Проверено тестами с фейковым отправителем.
  • calendar Синхронизация с Google Calendar работает при настроенном web-клиенте Google с включённым Calendar API и зарегистрированным redirect URI; проверена только тестами с фейковым Google API. Поллинг вместо push-уведомлений (watch channels требуют публичный https-эндпоинт).
  • digest Планировщик живёт в процессе API: при нескольких инстансах нужен выбор лидера или внешний cron, иначе выпуски задублируются. Зона пользователя известна серверу только после первого PUT /settings, до этого используется UTC.
  • sync Конфликты решаются правилом «сервер побеждает при первой загрузке, затем последний пишущий»; для нескольких устройств с офлайн-правками нужен вектор изменений или op-log.
  • files Вложения из сида без содержимого сервер не сохраняет (нет байтов для загрузки). Реальные файлы загружаются и хранятся.
  • ui В mobile курсив заголовка месяца не рендерится: у Golos Text нет italic-начертания, браузер его синтезирует, iOS нет.
  • env На машине разработки порт 5080 занят сторонним процессом, API запускается с --urls http://localhost:5081.
